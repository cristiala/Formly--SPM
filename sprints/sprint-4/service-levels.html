Sprint 4 / Service levels

Service Levels

Set honest targets for Formly's first form-feedback model, then define how the team will measure delivery and respond when something goes wrong.

← Sprint 4 overviewTargets proposed, not measured

01 / Service level objectives

Two initial model objectives

Each objective uses a rolling 28-day window once testing begins. The worked budgets below use 200 eligible cases only to illustrate the count; the actual allowance changes with the number evaluated. Allowed misses = floor(eligible cases × (100 − target percentage) ÷ 100).

0185% target

Useful guidance

At least 85% of reviewed completed form checks should give a cue a reviewer can understand and act on, with no clear safety concern under the team's written rubric.

Measure
Checks passing the rubric ÷ completed checks reviewed
Source
Sampled check outputs and reviewer decisions
Owner
Model quality owner — name to assign
Window
Rolling 28 days after testing starts
Error budget example30 missesOf 200 reviewed checks; 170 must pass.

Budget policy

At 15 misses in the example window, the model quality owner reviews failed cues and assigns a fix within one working day, telling the team lead and test owner the same day. At 30 misses, that owner pauses model changes that could worsen guidance, notifies those people immediately, and agrees on a recovery plan with them within one working day.

0280% target

Issue detection

At least 80% of labeled cases that contain a target form issue should have that issue flagged by the model. This measures recall on known issues.

Measure
Unique cases with the target issue correctly flagged ÷ unique labeled cases with that issue
Source
Labeled checks from the window, their outputs, and served model versions
Owner
Evaluation owner — name to assign
Window
Rolling 28 days after testing starts
Error budget example40 missesOf 200 labeled issue cases; 160 must be flagged.

Budget policy

At 20 missed issues in the example window, the evaluation owner checks missed cases by exercise, camera angle, and lighting within one working day, telling the model owner and team lead the same day. At 40 misses, the evaluation owner pauses expansion to new exercises, notifies those people immediately, and agrees on a retraining or scope plan with them within one working day.

The 50% and 100% triggers above should be recalculated from the actual budget when the evaluated case count differs from 200. A reviewer must approve the case labels and rubric before either percentage is published.

Method reference: Google SRE's error-budget policy.

03 / Responding to failure

Three severity levels

Times below are targets for acknowledging and beginning triage, not promises to fix an incident within that time. The examples are drafts for team review.

05 / Learning from incidents

Blameless incident review

Hypothetical team exercise — not an actual incident

This worked example asks what would happen if an exercise appeared saved, but its feedback was missing when reopened. The counts, times, and cause below are illustrative assumptions, not observations about a working Formly app. A real incident review must replace them with evidence and describe decisions without assigning personal blame.

  1. SummaryDuring a pilot release, the app showed “Saved” after storing an exercise entry, but its feedback was not stored. Reopening the exercise showed an empty feedback area. The team stopped the misleading save flow, restored the previous version, and confirmed that new saves reopened with feedback.
  2. ImpactIllustrative scope: 5 of 18 exercises saved before rollback had missing feedback. Those users could see their exercise entries but could not revisit their guidance. An audit would determine whether the feedback could be recovered; the visible entry alone does not prove that the feedback exists.
  3. TimelineT+0: save change released. T+25 minutes: first incomplete record. T+40: user report. T+55: team reproduced the issue and checked write logs. T+65: affected save flow paused and release rolled back. T+90: new save-and-reopen checks passed. Next working day: affected records audited and users updated.
  4. CausesAssumed for this exercise: the exercise entry and feedback were written separately, and the interface treated the first write as full success. A failed feedback write was neither shown to the user nor retried. Testing checked that an entry appeared, but did not reopen it to confirm that feedback was durable. No alert watched for entries without feedback.
  5. ResponseThe incident lead would treat a widespread pilot failure as SEV 2 and begin triage within the one-hour target. Roll back the faulty save path, then compare affected entries with retained check outputs. Reattach feedback only when it can be matched safely to the correct user and exercise; otherwise explain the gap and offer a new check. Close the incident after save-and-reopen verification and a user update.
  6. Action itemsApp data owner: make “Saved” depend on both records being durable, or show a pending state with a safe retry; verify with a forced feedback-write failure before the next pilot release. Test owner: add a save-and-reopen test that checks feedback content, due before that release. Delivery owner: alert on exercise entries without feedback and rehearse record recovery, due before that release.

Sprint 4

Set honest targets for Formly's first form-feedback model, then define how the team will measure delivery and respond when something goes wrong.

Initial build for team reviewTargets proposed, not measured

01 / Read this first

What these targets mean

These are proposed objectives for the initial machine learning model. They are not claims about a working product. The 85% and 80% targets allow room for early model variation while giving the team clear thresholds to test against.

Model quality and service health need separate measures. The objectives below judge the guidance Formly gives. The team should also record whether a form check starts, completes, and returns a result, without treating a server or camera failure as a model-quality miss.

This separation follows Google Cloud's AI/ML reliability guidance.

Before reporting a score: name the measurement owners, approve the review rubric and labeled cases, collect a representative sample, and record the sample size. If there are too few reviewed cases, report “insufficient data.”

02 / Service level objectives

Two initial model objectives

Each objective uses a rolling 28-day window once testing begins. The worked budgets below use 200 eligible cases only to illustrate the count; the actual allowance changes with the number evaluated. Allowed misses = floor(eligible cases × (100 − target percentage) ÷ 100).

0185% target

Useful guidance

At least 85% of reviewed completed form checks should give a cue a reviewer can understand and act on, with no clear safety concern under the team's written rubric.

Measure
Checks passing the rubric ÷ completed checks reviewed
Source
Sampled check outputs and reviewer decisions
Owner
Model quality owner — name to assign
Window
Rolling 28 days after testing starts
Error budget example30 missesOf 200 reviewed checks; 170 must pass.

Budget policy

At 15 misses in the example window, the model quality owner reviews failed cues and assigns a fix within one working day, telling the team lead and test owner the same day. At 30 misses, that owner pauses model changes that could worsen guidance, notifies those people immediately, and agrees on a recovery plan with them within one working day.

0280% target

Issue detection

At least 80% of labeled cases that contain a target form issue should have that issue flagged by the model. This measures recall on known issues.

Measure
Unique cases with the target issue correctly flagged ÷ unique labeled cases with that issue
Source
Labeled checks from the window, their outputs, and served model versions
Owner
Evaluation owner — name to assign
Window
Rolling 28 days after testing starts
Error budget example40 missesOf 200 labeled issue cases; 160 must be flagged.

Budget policy

At 20 missed issues in the example window, the evaluation owner checks missed cases by exercise, camera angle, and lighting within one working day, telling the model owner and team lead the same day. At 40 misses, the evaluation owner pauses expansion to new exercises, notifies those people immediately, and agrees on a retraining or scope plan with them within one working day.

The 50% and 100% triggers above should be recalculated from the actual budget when the evaluated case count differs from 200. A reviewer must approve the case labels and rubric before either percentage is published.

Method reference: Google SRE's error-budget policy.

05 / Learning from incidents

Blameless incident review

Template awaiting a real incident

Use this after an actual incident. Describe the conditions and decisions using evidence available at the time; do not assign personal blame. This section does not claim that a review has already happened.

  1. SummaryWhat happened, when, and what was restored?
  2. ImpactWhich users, exercises, and checks were affected? For how long?
  3. TimelineWhat did logs and team messages show, in time order?
  4. CausesWhich model, data, code, process, or environment conditions contributed?
  5. ResponseWhat actions helped, and where did detection or coordination slow down?
  6. Action itemsList a concrete change, owner, due date, and verification for each item.
